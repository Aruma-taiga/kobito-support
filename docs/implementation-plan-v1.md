## 1. 結論

- **6週で「通し確認」まで作れる見込み**（WBSの6.7が第6週）。第7週にリハーサル、第8週にプレオープン、というWBSの枠に収まります。
- 一番の危険は、コードではなく**外の手続きの待ち時間**です：KOMOJUの加盟店審査（カードは承認が必要）、LINE公式・LIFFの設定、メール送信のドメイン設定、サービス名の商標・ドメイン。**第1週にまとめて申し込む**のが条件です。
- 作る順番は、**「申込み → 審査 → 請求書 → 入金 → 契約成立」の1本を、最初に端から端まで通す**。そのあとで毎月の処理、依頼と見積、報酬を足します。

## 5. つくり方のルール

- **端から端まで通す順**（縦に切る）。画面だけ・データベースだけ先に作らない。
- **お金・期間・状態は先にテストを書く**：税の端数、月末の期間、クレジットの残り（予約・消費・失効）、請求書の採番、Webhookの二重受信。ここは間違うと取り返しがつかないので、テストを厚くする。
- **KOMOJUとLINEは偽物に差し替えられる形**にして、テストはお金を動かさずに回す。本番に近い確認は、KOMOJUのテスト環境で。
- **お客様の情報の絞り込み**（他のお店の情報が見えない）は、API全体の自動テストで確かめる（設計書2章）。
- 環境は「開発」「本番」の2つ。本番のデータベースはバックアップを有効にし、設定は Terraform と Secret Manager で管理する。
- 変更はpull requestで出し、taigaさんが見られる確認用の画面（開発環境）をいつでも開ける状態にする。

## 6. 遅れたときの後回しの順

第4週の終わりに「端から端まで通る」が守れない場合、次の順に後回しにします。

| 後回しにするもの | 代わりにやること |
|---|---|
| ① パートナー報酬の画面 | 報酬は SQL / CSV で月1回計算して、手で支払う（最大20社） |
| ② LINE連携ログイン・LIFF | メール＋パスワードだけで出す。LINEは通知のみ |
| ③ コンビニ払い | カードと銀行振込だけで出す（LP・申込フォームの支払方法の記載は合わせる） |
| ④ 個別見積りのプランの画面 | 個別見積りの申込みは、管理画面から手で契約を作る |
| ⑤ 削除の自動処理 | 「削除予定一覧」を見て手で消す（解約から1年後なので急がない） |

**後回しにしないもの：** 申込み・同意の記録、審査、請求書の自動発行と採番、カード・振込の入金、契約成立、クレジットの付与・失効、マイページの見積了承、カード失敗の通知、アクセス制限のテスト、バックアップ。

## 7. リスク

| リスク | 影響 | 備える |
|---|---|---|
| KOMOJUの加盟店審査が長引く | 本番のカード決済が使えず、リハーサルが遅れる | 第1週に申込み。テスト環境で開発を進め、審査中も止めない。遅れたら銀行振込だけで出す手もある |
| カードの結びつけが成り立たない | 設計の変更（顧客IDを持つ） | 第1週の試作で早く分かる。「カード情報を持たない」の方針は保てるので、相談は軽いはず |
| サービス名・ドメインが未確定（商標調査中） | ドメイン、メールの送信元、LINEの設定がやり直しになる | 名称は設定値で差し替え可能（G-01）。公開直前まで仮のドメインで進め、メールの送信元ドメインだけは確定後に設定 |
| 規約・特商法・弁護士の確認が間に合わない | 申込フォームの文言が変わる（実装は小さい） | 文言は設定値・画面の文章として分けておく。公開前に差し替え |
| 範囲が広い（申込み・決済・請求・マイページ・管理画面・LINE） | 6週に収まらない | 6章の後回しの順 |

## 8. 通し確認の項目（第6週、WBS 6.7）

1. 紹介コード付きで申込み → 審査 → 請求書（カード）→ テスト決済 → 契約成立 → クレジット付与
2. 同じ流れを銀行振込（手で消込）とコンビニで
3. 7日以内に払わず、失効する
4. 依頼 → 見積 → マイページで了承（残りが足りないと押せない）→ 完了 → 消費
5. 日付を1か月進めて、請求書・付与・失効が1回だけ起きる（二重に起きない）
6. カード失敗 → 翌日と3日後の通知 → 再決済で復旧
7. 解約 → 期間の終わりで終了、定期課金が止まる、報酬が止まる
8. 他のお店の情報が見えない／管理画面は2段階認証なしで入れない
9. バックアップからの復元
